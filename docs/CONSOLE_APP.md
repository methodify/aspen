# The console as an app: installable, resilient, hosted, on a phone

v0.26 (PROPOSALS-2026-09-D.md, D-1/D-2/D-3/D-10). The console the node
serves and the console at `https://methodify.github.io/aspen/` are one
build in two shapes.

## 1. Installable (D-1)

`manifest.webmanifest` (generated by `vite-plugin-pwa` from
`ui/vite.config.ts`): name Aspen, standalone display, the mark as icons
(192/512 and maskable, `ui/public/icons/`, rasterized from
`aspen-mark.svg`), shortcuts to Now, Search and Boards, and a
`web+aspen://` protocol handler. The status bar offers **install** when
the browser allows it (`beforeinstallprompt`); an installed app has its
own window and a dock icon carrying the **needs-you count** as a badge
(`navigator.setAppBadge`, cleared at zero).

`web+aspen://session/<agent>` opens the session; `web+aspen://connect?relay=&node=`
opens the connect page with those filled in. Both land on `/open?u=`.

Installs are per origin: the node on this machine at `127.0.0.1` is one
app, the hosted console another. `http://` origins other than loopback
never get an install prompt — the hosted console is where the app is one
thing.

## 2. The service worker (D-2)

Workbox, `registerType: prompt`. It precaches the shell only — HTML, JS,
CSS, the mark, the icons — and never touches `/api`: a stale fleet is
worse than none, so nothing under `/api` is cached and the shell is never
served for an API path. What it gives:

- **The shell survives the node.** Reload during `aspen update
  --restart` or a relaunch and the console opens to *connecting…* and
  comes back when the node does, instead of a browser error page.
- **Its own update flow.** A new build installs in the background; the
  status bar shows **new console — reload**; nothing takes over
  mid-session.
- **A place for push** (D-4, next round).

## 3. Hosted (D-3)

The console is built with `VITE_HOSTED=1` (base `/aspen/`, hash routes
because a static host has no SPA fallback, `__ASPEN_HOSTED__` true).
`pages.yml` publishes it to GitHub Pages; the release workflow dispatches
it on `main` after each tag (the Pages environment deploys from `main`
only), and `gh workflow run pages.yml --ref main` does the same by hand; the release workflow attaches
`console.zip` for anyone hosting it themselves. One-time repository
setting: Pages source = GitHub Actions.

**Connections** (`ui/src/connections.ts`). Hosted, the console keeps a
named list, one active:

- **direct** `{url, token}` — a node reached by URL. From an `https`
  page that can only be the node on this machine (`http://127.0.0.1:…`
  is a "potentially trustworthy" URL; a LAN address is mixed content and
  the browser blocks it — the connect page says so before trying). The
  node must allow the origin: `aspen config console-origins` (default
  `https://methodify.github.io`; comma-separated; `-` restores the
  default). The node answers CORS for listed origins only, with Chrome's
  Private Network Access preflight (`Access-Control-Allow-Private-Network`),
  and the token travels in `X-Aspen-Token` as before.
- **relay** `{relay, node}` — the console as a mesh peer (RELAY.md §11),
  unchanged; the identity, certify and relay steps on the connect page
  are the same, and "save relay → node" keeps them as a connection.

Connecting in step 3 saves the relay and node as a connection and makes
it the active one; the console counts an attached tunnel as connected
whether or not it was saved (v0.26.1 — before, the hosted console bounced
every route back to Connect until a connection was saved by hand). A
node that hosts a relay is present on it, so it can be the node you
attach to (RELAY.md §11).

Files (the artifact viewer) come over the tunnel too (v0.26.3): the
bytes arrive base64 in the `http` op's answer and become a blob URL for
the image, the raw link and the download; images a rendered document
refers to by relative path are not fetched through the tunnel yet.

`api.ts` prefixes every request and the events WebSocket with the active
direct connection's URL; a relay connection turns the tunnel on. With no
active connection the hosted console opens on the connect page. The
status bar shows the connection's name (direct) or *via relay → node*.

**Versions.** Hosted, the console and the node move on separate trains:
the badge reads *node v… · console v…*, and a node older than the
console's minimum (`MIN_NODE_VERSION` in `App.tsx`, 0.25.0) gets a red
*too old for this console* badge instead of a broken page. Features gate
on `capabilities` and on the presence of fields, not on version
arithmetic.

## 4. On a phone (D-10)

`ui/src/phone.css`, at 720 px and below: one column; the rail becomes a
bottom bar of Now, Flow, Mesh, History, Search and Boards (Plugins and
Usage stay reachable by URL and the palette); the status bar keeps the
mark, the version badge, the connection pill and the bell; the session
page's controls strip scrolls sideways and the composer sits above the
bar; cards stack; dialogs and the palette fill the width; toasts sit
above the bar. Boards and the mesh views carry a note that they are laid
out for a wider screen.

## 5. Verified (2026-09-09)

Hosted bundle served from a second local origin, node's
`console-origins` set to it: the connect page opened first, a direct
connection to the rig node worked — Now, sessions and live events — with
the CORS and private-network headers confirmed on the preflight;
manifest and worker served by the node with the right content types;
the worker registered and offered install. Phone layout checked at
400 px. GitHub Pages deployment runs on the next tag.
